כלי פנימי עם Claude Code נבנה בשלושה שלבים: מגדירים בעיה אחת קטנה וחוזרת, נותנים לסוכן לבנות גרסה ראשונה על נתוני דוגמה, ומשפרים לפי שימוש אמיתי של הצוות. במדריך הזה נעבור על דוגמה טיפוסית לצוות תפעול: טבלת בקשות ציוד שמתנהלת בשרשורי מייל והופכת לאפליקציה קטנה עם טופס, סטטוסים והתראות. נראה איך בוחרים את הבעיה, תוכנית עבודה של יומיים, מה נוטה להישבר, ואיך מחשבים אם זה השתלם.

## איזה כלי פנימי עם Claude Code שווה לבנות קודם?

הטעות הנפוצה היא להתחיל מהכלי הכי שימושי. מתחילים מהכלי הכי פשוט שעדיין כואב. שלושה קריטריונים לבדוק:

- **התהליך חוזר על עצמו** לפחות פעם בשבוע, ולוקח לפחות שעה בכל פעם.
- **הקלט והפלט ברורים.** אפשר להסביר למתמחה חדש בשתי דקות מה נכנס ומה יוצא.
- **אין מערכת ליבה באמצע.** לא נוגעים ב-ERP, בשכר או בנתוני לקוחות בכלי הראשון.

<div class="definition">**כלי פנימי:** תוכנה קטנה שמשרתת צוות אחד בארגון ולא לקוחות חיצוניים: טופס, דשבורד, סקריפט, בוט. בדרך כלל לא נבנית כי היא "לא מספיק חשובה" לצוות הפיתוח, ולכן נשארת באקסל ובמייל.</div>

שיטה שעובדת: אספו רעיונות מכל הצוותים, העבירו כל רעיון דרך שלושת הקריטריונים, ומתוך מה שנשאר בחרו את הפשוט ביותר. רוב הרעיונות ייפלו, וזה בסדר. הרשימה שנשארת היא תוכנית העבודה לחודשים הבאים. על הגישה הכללית לכלי ועל מה עוד אנחנו בונים איתו יש הרחבה במרכז הנושא [Claude Code לארגונים](/topics/claude-code).

שאלה שעוזרת לבחור: אם הכלי ייעלם מחר, מי יצעק? אם התשובה היא "אף אחד", זה לא הכלי הראשון. אם התשובה היא "צוות אחד, בקול רם", מצאתם.

## דוגמה טיפוסית: מה היה לפני ומה אחרי?

זו דוגמה להמחשה, לא סיפור של לקוח. היא מייצגת בעיה שקיימת בהרבה צוותי תפעול.

**לפני.** עובד שצריך ציוד שולח מייל לרכז התפעול. הרכז מעתיק לגיליון, עונה במייל, מעדכן סטטוס ידנית, ושולח מייל נוסף כשהציוד מגיע. בקשות הולכות לאיבוד, ואנשים שואלים שוב ושוב "מה קורה עם הבקשה שלי".

**אחרי.** עמוד פנימי עם טופס קצר. כל בקשה נשמרת במסד נתונים עם סטטוס. הרכז רואה טבלה, משנה סטטוס בלחיצה, והמבקש מקבל מייל אוטומטי בכל שינוי. יש עמוד "הבקשות שלי" לכל עובד. בלי התחברות מסובכת, אלא לפי כתובת המייל הארגונית.

מה כדאי למדוד כדי לדעת אם זה עבד: כמה זמן בשבוע הרכז מקדיש לניהול בקשות, כמה פעמים שואלים אותו "מה קורה עם הבקשה", וכמה בקשות הולכות לאיבוד. מדדו את שלושתם שבועיים לפני שמתחילים לבנות.

## איך בונים את הכלי צעד אחרי צעד?

תוכנית עבודה מומלצת ליומיים. הזמנים בסוגריים הם הקצאה מתוכננת, לא הבטחה:

1. **יום 1, בוקר: אפיון בעמוד אחד (שעה).** יושבים עם הרכז וכותבים: מי המשתמשים, מה השדות בטופס, מה הסטטוסים, מתי נשלח מייל. זה הקובץ שהסוכן מקבל ראשון.
2. **יום 1: קובץ הנחיות לפרויקט (20 דקות).** קובץ טקסט קצר בתיקייה: מה הפרויקט, איזה סטאק, מה אסור (לא למחוק נתונים, לא לשנות סכמה בלי לשאול). Claude Code קורא אותו בכל הפעלה.
3. **יום 1: גרסה ראשונה על נתוני דוגמה (3 שעות).** מבקשים טופס, טבלה ומסד נתונים. הסוכן מקים פרויקט, מחבר Supabase, ובונה שני עמודים. בודקים עם 20 בקשות מומצאות.
4. **יום 1, אחר הצהריים: הרכז מנסה (שעה).** כמעט תמיד הוא ימצא משהו שחסר, למשל שדה "דחיפות" או מיון לפי תאריך. כל הערה כזו הופכת לבקשה קצרה לסוכן.
5. **יום 2, בוקר: התראות מייל (שעתיים).** חיבור לשירות מייל, תבנית לכל שינוי סטטוס. בקשו מהסוכן לכתוב גם בדיקה שמוודאת שמייל לא נשלח פעמיים.
6. **יום 2: עמוד "הבקשות שלי" והרשאות (שעתיים).** הפרדה בין מה שרואה עובד למה שרואה הרכז. זה החלק שכדאי לבקש ממפתח לעבור עליו, גם אם רק לזמן קצר.
7. **יום 2, אחר הצהריים: פריסה וניסוי עם 5 אנשים (שעתיים).** מעלים לכתובת פנימית. חמישה עובדים שולחים בקשות אמיתיות. את הבאגים שהם מוצאים מתקנים לפני המעבר המלא.
8. **שבוע אחרי: מעבר מלא.** המייל הישן מקבל תשובה אוטומטית עם קישור לטופס.

## איזה סטאק טכנולוגי לבחור?

Claude Code לא מחייב סטאק. הכלל שלנו: הכי פשוט שעונה על הצורך.

| סוג כלי | מה בוחרים | למה | דוגמה |
| --- | --- | --- | --- |
| סקריפט שרץ על קובץ | Python בלבד | אפס תשתית, קל להריץ שוב | איחוד דוחות, ניקוי נתונים |
| טופס או דשבורד לצוות | אפליקציית web קטנה עם Supabase | מסד נתונים, הרשאות ואירוח בלי שרת משלכם | טופס הבקשות מהדוגמה |
| תהליך בין מערכות | n8n, ו-Claude Code לחלקים המורכבים | חיבורים מוכנים, ניטור ויזואלי | פנייה נכנסת שפותחת כרטיס |
| אתר תוכן פנימי | אתר סטטי | מהיר, זול, בלי מסד נתונים | מאגר נהלים |

את האתר הזה, למשל, בנינו כאתר סטטי עם Claude Code, והסיפור המלא בעמוד [איך בנינו את האתר](/how-this-site-was-built). כשהכלי צריך לדבר עם מערכות אחרות, אנחנו משלבים n8n, כמו במאמר על [סוכן AI עם n8n](/blog/n8n-ai-agent).

## מה נוטה להישבר בדרך ואיך מתקנים?

- **הסוכן "משפר" דברים שלא ביקשתם.** למשל, משנה את עיצוב הטבלה כשביקשתם רק להוסיף שדה. תיקון: שורה בקובץ ההנחיות, "לא לשנות דברים שלא התבקשו, להציע במקום".
- **מיילים כפולים.** שינוי סטטוס ששולח שני מיילים. בדיקה אוטומטית תופסת את זה לפני הפריסה. בלי בדיקות, תגלו את זה מהמשתמשים.
- **הרשאות פתוחות מדי.** בגרסה ראשונה קל לקבל מצב שבו כל עובד רואה את כל הבקשות. מפתח שעובר על הקוד יתפוס את זה מהר. זו הסיבה שמעבר אחד של מפתח שווה את הזמן.
- **נתוני דוגמה שלא דומים למציאות.** בקשות אמיתיות כוללות, למשל, טקסט ארוך בשדה "הערות" שלא נכנס לטבלה. התיקון קטן, אבל הלקח חשוב: קובץ הדוגמה צריך להיות מכוער כמו המציאות.

## איך דואגים שהכלי ישרוד אחרי שבוע?

כלים פנימיים נוטים למות לא כי הם לא עובדים, אלא כי אין להם בעלים. ארבעה דברים שכדאי לעשות:

- **בעלים אחד עם שם.** הרכז. הוא לומד להפעיל את Claude Code על התיקייה ולבקש שינויים קטנים בעצמו, בלי לחכות למפתח.
- **קובץ README שהסוכן כתב.** איך מריצים, איך משנים שדה, למי פונים. בקשו מהסוכן לעדכן אותו בכל שינוי.
- **נקודת שמירה לפני כל שינוי.** git, עם הודעות שהסוכן כותב. כששינוי שובר משהו, חוזרים אחורה בלי דרמה.
- **גבול ברור למה הכלי לא עושה.** כשבקשות להרחבה מתחילות להגיע (אישורים, תקציב, הזמנה מספק), כותבים בקובץ ההנחיות מה הכלי לא יעשה. כלי קטן שעובד עדיף על כלי גדול שאף אחד לא מתחזק.

## כמה זה עולה ואיך מחשבים את החיסכון?

העלות מורכבת מארבעה רכיבים: הזמן של מי שבנה, הזמן של המפתח שעבר על ההרשאות, קריאות למודל בזמן הבנייה, ואירוח. את מחיר הקריאות בודקים בדף התמחור של הספק, למשל [דף התמחור של Claude](https://claude.com/pricing), ואת האירוח בתוכנית של שירות האירוח שבחרתם. החיסכון: השעות השבועיות של הרכז לפני ואחרי, כפול עלות שעה טעונה. את הזמן של עובדים שהפסיקו לשאול "מה קורה עם הבקשה" קשה למדוד, ולכן רושמים אותו כתועלת איכותית ולא מכניסים לחישוב. עוד על מדידה כזאת במרכז הנושא [ROI של AI](/topics/ai-roi).

מה שחשוב יותר מהכלי עצמו: האם מי שבנה אותו בונה את הכלי הבא לבד. זה המדד שכדאי לחפש.
