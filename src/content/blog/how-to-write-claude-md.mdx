קובץ CLAUDE.md הוא קובץ טקסט שיושב בתיקיית הפרויקט, ו-Claude Code קורא אותו בתחילת כל שיחה. כותבים בו רק מה שהסוכן לא יגלה לבד מקריאת הקוד: הפקודות המדויקות להרצה ולבדיקה, מוסכמות שסוטות מברירת המחדל, מלכודות ידועות, והחלטות שלא כתובות בשום מקום. מומלץ להישאר מתחת ל-200 שורות, כי כל שורה נוספת מחלישה את כל השאר.

<div class="definition">**CLAUDE.md:** קובץ Markdown עם הוראות קבועות ל-Claude Code. הוא נטען לקונטקסט בתחילת השיחה כהודעה מהמשתמש, אחרי הנחיות המערכת. Claude קורא אותו ומשתדל לקיים, אבל זו לא הגדרה שנאכפת, ולכן הוראה מעורפלת או סותרת עלולה להיות מוזנחת.</div>

## איפה יושב קובץ CLAUDE.md, ואיזה קובץ גובר?

יש כמה מקומות, וכולם נטענים יחד. הקבצים לא דורסים זה את זה. התוכן שלהם מחובר, מהרחב אל הספציפי, כך שמה שקרוב יותר לתיקייה שממנה הפעלתם את Claude נקרא אחרון.

| קובץ | נתיב | למה משמש |
|---|---|---|
| מדיניות ארגונית | נתיב מערכת | כללים לכל הארגון. מפתחים לא יכולים להחריג אותו |
| משתמש | `~/.claude/CLAUDE.md` | העדפות אישיות שלכם לכל הפרויקטים |
| פרויקט | `./CLAUDE.md` | הוראות משותפות לצוות, נשמר ב-git |
| מקומי | `./CLAUDE.local.md` | העדפות אישיות לפרויקט הזה, מחוץ ל-git |
| כללים | `.claude/rules/` | קבצים נפרדים לפי נושא, אפשר להגביל לנתיבים |

את קובץ הפרויקט אפשר לשים גם בתוך `.claude/`, בנתיב `./.claude/CLAUDE.md`, אם רוצים שורש נקי. ועוד שני פרטים שחוסכים בלבול. קובץ CLAUDE.md בתת תיקייה לא נטען בהפעלה. הוא נכנס רק כש-Claude קורא, כותב או עורך קובץ באותה תיקייה, ולכן מתאים למונורפו שבו לכל חבילה יש מוסכמות משלה. ואם רוצים לראות מה בדיוק נטען, מריצים `/context`. הפקודה `/memory` מציגה את כל הקבצים ופותחת כל אחד לעריכה.

## מה כותבים בקובץ CLAUDE.md ומה משאירים בחוץ?

התיעוד של Claude Code מציע מבחן של שתי שאלות לכל שורה: האם Claude יכול למצוא את זה בקריאת הקוד? והאם הוא באמת ילך לחפש? אם התשובה לשתיהן היא כן, השורה מיותרת. תיאור של מבנה התיקיות, רשימת תלויות או סקירת ארכיטקטורה הם דוגמאות קלאסיות למה שהוא קורא לבד.

מה כן נכנס:

- **פקודות מדויקות.** איך מתקינים, איך מריצים בדיקה של קובץ אחד, איך מריצים בדיקת טיפוסים ו-lint. לא "תבדוק את השינויים", אלא `npm test` עם הדגל הנכון.
- **מוסכמות שסוטות מהרגיל.** איזה helper משתמשים בו לשגיאות, באיזו תיקייה יושבים ה-handlers, איזה קוד ישן חי אבל אסור להעתיק ממנו.
- **מלכודות.** משתנה סביבה שבלעדיו הבדיקות נופלות, שירות שצריך להרים קודם, קובץ שנוצר אוטומטית ואסור לערוך ידנית.
- **החלטות שלא כתובות בקוד.** למשל, למה בחרתם בספרייה מסוימת ולא באחרת, כדי שהסוכן לא "ישפר" את זה.
- **כל דבר שתיקנתם פעמיים.** זה הקריטריון הכי מעשי שיש בתיעוד. אם הסברתם את אותו הדבר בשתי שיחות, מקומו בקובץ.

מה נשאר בחוץ: עצות כלליות כמו "כתוב קוד נקי", הסברים שכבר מופיעים ב-README, ותהליכים ארוכים של כמה שלבים. לפי התיעוד, ככל שההוראות ספציפיות ותמציתיות יותר, Claude מקיים אותן בעקביות רבה יותר. "השתמשו בהזחה של 2 רווחים" עובד. "פרמטו את הקוד כמו שצריך" לא.

## איך כותבים CLAUDE.md טוב מאפס?

1. **מריצים `/init` בתיקיית הפרויקט.** Claude סורק את הקוד ומייצר טיוטה עם פקודות בנייה ובדיקה ומוסכמות שזיהה. אם כבר יש קובץ, הוא מציע שיפורים במקום לדרוס.
2. **מוחקים את מה שהוא יכול לגלות לבד.** הטיוטה כוללת בדרך כלל תיאור מבנה ורשימות. רוב השיפור מגיע מהמחיקה.
3. **מוסיפים את שלוש הפקודות שהכי חשובות.** התקנה, בדיקה של קובץ בודד, בדיקת טיפוסים. מעתיקים מהטרמינל, לא מהזיכרון.
4. **מוסיפים סעיף מלכודות.** מה שבטוח יכשיל מישהו חדש בפרויקט.
5. **מפעילים שיחה חדשה ובודקים עם `/context`** שהקובץ באמת נטען.
6. **עובדים שבוע, ומוסיפים שורה רק אחרי תיקון שני.** לא לפני.
7. **פעם בחודש מוחקים.** הוראות שהתיישנו או סותרות זו את זו גרועות מהיעדר הוראה. כשיש שתי הוראות סותרות, Claude עלול לבחור אחת באקראי.

## תבנית CLAUDE.md להעתקה

התבנית הזו בנויה על המבנה שהתיעוד הרשמי מדגים: פקודות (Commands), מוסכמות (Conventions), מלכודות (Gotchas), והוספנו סעיף החלטות (Decisions). היא כתובה באנגלית, כמו הדוגמאות בתיעוד, אבל עברית עובדת באותה מידה. מחליפים את הערכים בשלכם ומוחקים כל שורה שלא רלוונטית.

```markdown
# Commands
- Install: npm ci
- Run one test file: npx vitest run path/to/file.test.ts
- Typecheck: npx tsc --noEmit
- Before every commit: npm run lint

# Conventions
- Throw errors only via the helpers in src/lib/errors.ts, never raw strings
- src/legacy/ is still live, but don't copy its patterns into new code
- User-facing text in Hebrew, identifiers in English

# Gotchas
- Integration tests need DATABASE_URL, see .env.example
- Files in src/generated/ are generated, never edit them by hand

# Decisions
- No ORM. All queries live in src/db/queries/ so we control performance
```

עוד שלושה דברים שימושיים. הערות HTML בקובץ, בפורמט `<!-- -->`, מוסרות לפני שהתוכן נשלח ל-Claude, כך שאפשר להשאיר הערות לצוות בלי לבזבז קונטקסט. ייבוא עם `@` ונתיב, כמו `@docs/git.md`, מכניס קובץ נוסף, עד ארבע רמות עומק. אבל ייבוא לא חוסך מקום: הקובץ המיובא נטען יחד עם זה שמייבא אותו.

## מתי להוציא הוראה מ-CLAUDE.md?

קובץ CLAUDE.md מחזיק עובדות שרלוונטיות בכל שיחה. כל השאר עובר למקום אחר, וזה מה שמשאיר אותו קצר.

| ההוראה | לאן היא הולכת | למה |
|---|---|---|
| נכונה בכל שיחה, קצרה | CLAUDE.md | נטען תמיד |
| נוגעת רק לתיקייה מסוימת | `.claude/rules/` עם `paths` | נטען רק כשנוגעים בקובץ תואם |
| תהליך של כמה שלבים | סקיל | רק התיאור בקונטקסט, הגוף נטען כשמשתמשים |
| אסור שתישבר אף פעם | hook או כלל חסימה | נאכף בקוד, לא תלוי בקריאה |

איך כותבים סקיל כזה, צעד אחרי צעד, מוסבר במדריך [Claude Skills](/blog/claude-skills-guide).

כלל לפי נתיב הוא קובץ Markdown רגיל בתיקיית `.claude/rules/`, עם שדה `paths` בראשו, למשל `"src/api/**/*.ts"`. הוא נטען רק כש-Claude קורא או עורך קובץ שתואם לתבנית. על סקילים, ועל איך הם הופכים תהליכי עבודה לתיעוד שגם רץ, כתבנו במאמר [סקילים של AI בארגון](/blog/ai-skills-in-the-organization).

## למה Claude Code מתעלם מהוראה שכתובה בקובץ?

ברוב המקרים יש אחת משלוש סיבות. הקובץ ארוך מדי, וההוראה הולכת לאיבוד. יש הוראה אחרת שסותרת אותה, אולי בקובץ המשתמש או בכלל ישן. או שההוראה מעורפלת מכדי שאפשר לבדוק אותה.

האינסטינקט הוא להוסיף IMPORTANT באותיות גדולות. התיעוד אומר במפורש שזה כנראה לא יעזור: מודלים עדכניים מקיימים שורה פשוטה, והדגשה מוגזמת גורמת להם להחיל את הכלל גם במקומות שלא צריך. אם השורה הולכת לאיבוד, הקובץ צריך להיות קצר יותר. אם זה כלל שאסור לשבור, למשל לא לדחוף ישירות ל-main, הוא שייך ל-hook או לכלל חסימה בהגדרות, שנאכפים בלי קשר למה שהמודל זוכר.

## איך מנהלים את זה בארגון עם כמה צוותים?

בארגון יש שלוש שכבות, וכדאי להחליט מראש מי אחראי על כל אחת. ה-IT או צוות הפלטפורמה מנהלים את קובץ המדיניות הארגוני, שיושב בנתיב מערכת קבוע בכל מחשב (ב-Linux זה `/etc/claude-code/CLAUDE.md`). מפתחים יכולים להחריג קבצים אחרים שלא רלוונטיים להם, אבל לא את הקובץ הזה. לכן זה המקום לכללים כמו איפה מותר לשמור נתוני לקוחות, ולא להעדפות סגנון.

כל צוות מחזיק את קובץ הפרויקט שלו ב-git, עם בעלים ברור. וכל אחד מחזיק את ההעדפות שלו בקובץ המשתמש. הסדר הזה מונע תקלה מוכרת: שלושה אנשים שמוסיפים כל אחד את מה שחשוב לו לקובץ המשותף, עד שהוא ארוך פי כמה מ-200 השורות המומלצות, ואף אחד לא מעז למחוק.

## אילו טעויות הכי נפוצות בקובץ CLAUDE.md?

- **להעתיק את ה-README.** הסוכן כבר יכול לקרוא אותו. מספיק `@README` אם באמת צריך.
- **לכתוב מדריך הצטרפות.** עשרה שלבים של הקמת סביבה הם סקיל, לא עובדה.
- **לערבב אישי וצוותי.** "תענה לי בקצרה" שייך לקובץ המשתמש או ל-CLAUDE.local.md, לא לקובץ שכל הצוות מקבל.
- **לא לגעת בקובץ חודשים.** פקודה שהשתנתה בקובץ גרועה יותר מפקודה שחסרה, כי הסוכן יריץ אותה בביטחון.
- **לא להכניס אותו לסקירת קוד.** שינוי בקובץ משנה את ההתנהגות של כל מי שעובד בפרויקט. זה ראוי ל-PR כמו כל שינוי אחר.
